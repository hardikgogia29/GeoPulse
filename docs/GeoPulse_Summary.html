End-to-end ML system: 79M-row spatiotemporal forecasting pipeline, four model families, and an agentic map application

1. What it does

New York's Citi Bike has ~2,400 docking stations. Bikes pile up where people ride to and vanish from where people ride from — every weekday morning thousands flow into Midtown, leaving residential docks empty. GeoPulse predicts that flow before it happens, then makes the forecast usable: a map app where you ask "will I find a bike near Times Square?" and get a real answer with walking directions and an explanation.

2. The four research questions

#QuestionAnswer
RQ1How big should a map cell be? H3 resolution 8 (~0.74 km²). Chosen by skill score, because every ordinary metric is biased by cell size and the three we tried disagreed completely.
RQ2Hexagons or squares? Near coin flip. S2-13 scores slightly higher skill, but its cells are 47% larger — which plausibly explains the whole gap. Size matters; shape barely does.
RQ3Do deep models beat gradient boosting? No. Tuned LightGBM won at both grids. Two apparent deep-learning wins at H3-8 reversed at S2-13, so they were noise. Caveat in §7.
RQ4Do better forecasts improve operations? Yes between forecasts, no in absolute terms. LightGBM beat even a perfect forecast at rebalancing — but rebalancing itself didn't help. §8.

4. Data and cleaning

Four sources: Citi Bike trips (90 monthly CSVs), weather (Open-Meteo hourly, 17,544 rows, no gaps), events (557,674 NYC permit records) and traffic (Socrata API, 23,758,184 readings).

A false start worth recording

The traffic CSV downloaded from the NYC Open Data web UI opened cleanly and looked correct. It had been silently row-capped and contained only five days from July 2018 — zero overlap with the project window. Caught only because a check compared the file's date range against the project's. Refetched via the Socrata API, paginating by time window rather than row offset, and completeness was proved against a server-side count(1).

The cleaning waterfall

Nine named rules, applied in order; each removed row attributed to the first rule it violates, so counts sum exactly to the total. A quality report is produced before anything is deleted.

Daylight saving — the problem nobody expects

Citi Bike publishes naive local time. In November the 1–2 am hour happens twice, written identically both times; bin it in local time and one interval gets double demand. In March that hour doesn't exist. Everything is stored in UTC instead, and the damage was measured rather than assumed:

UTC hourRidesMeaning
2023-11-05 05:002,921Both passes collapsed together
2023-11-05 06:000The unreachable second pass
2024-11-03 05:00 / 06:003,534 / 0Same pattern next year

Four affected hours are flagged dst_unreliable and excluded from every model, so nothing learns the artificial collapse.

Sorting 79 million rows

A global ORDER BY spilled 8 GB and hadn't finished after an hour. Because the data is already partitioned by month, sorting each month (~3M rows, in memory) and concatenating in month order gives the identical ordering — 90 seconds. Verified two independent ways: 0 inversions across 79,165,067 rows.

5. The panel and the features

The panel is exactly one row per cell per 15-minute interval, no gaps. A cell with no trips gets a 0, not a missing row — because "four rows back" only means "one hour ago" if every interval is guaranteed present.

PropertyValue
Rows104,071,008 = 1,483 cells × 70,176 intervals — exactly dense
ReconciliationPanel pickups 79,150,890 — matches trips in active cells exactly
Active cells1,483 of 1,570 touched, carrying 99.98% of all endpoints
Targets15/30/45/60 min ahead × pickups/dropoffs, re-derived by independent join
End of seriesNULL, never 0 — a zero teaches a phantom demand collapse

Preventing leakage

Forecast time is pinned to the END of an interval. That makes a one-step forecast genuinely 15 minutes ahead, and makes the just-completed interval a legal input — the single most informative feature, which an earlier phase had omitted.

Proof, not inspection

15 tests re-derive every lag feature by an independent timestamp self-join and assert agreement; 20 more cover the advanced families. Reading code catches the bugs you thought of; re-deriving the answer a different way catches the ones you didn't.

Traffic got a fair second chance

The first ablation ran at H3-9, where traffic sensors reach only 5.1% of cells — that tests "traffic in 5% of Manhattan", not "traffic". Gain-based importance from the trained model agrees independently: the top five features are pickups_ewm_4, pickups_roll_mean_4, pickups_lag_0, pickups_slot_expanding_mean, pickups_roll_sum_4 — all from families A, B and C.

6. Choosing the cell size — and why the obvious metric lies

ResolutionCellsArea km²% zeroMAEWAPEHotspot F1Skill
H3-83210.74147.5%1.6540.3080.7480.2563
H3-91,4830.10671.4%0.7050.6050.5900.1920
H3-102,1620.01575.6%0.5800.7310.4810.1791

MAE says resolution 10. WAPE and Hotspot F1 say resolution 8. That total disagreement is the clue that none of them measures skill:

  • MAE falls automatically as cells shrink — smaller cells hold smaller counts. In the limit, a cell that always contains zero has perfect MAE and zero use.
  • WAPE falls automatically as cells grow — aggregation smooths relative error. In the limit, one cell covering all of NYC scores beautifully and says nothing.
  • Hotspot F1 depends on cell count — top 10% of 321 is a different task from top 10% of 2,162.

The fix is a skill score: 1 − model_MAE / naive_MAE, both computed on the same grid, so the scale effect cancels. Resolution 8 wins, and also wins on sparsity (47.5% empty vs 75.6%).

RQ2: S2 level 13 was selected by a matching procedure (weighted log-ratio distance on area and cell count; score 0.319 vs 0.951 for the next candidate), not guessed. It edges H3-8 on skill (0.274 vs 0.256) — but its cells are still 47% larger, which plausibly accounts for the entire gap. Resolution is the decision that matters.

7. Models and the test set

LightGBM — objective tested not assumed (Poisson 1.5695 beat L1 1.5739); the old 500-round cap was genuinely binding, so it was raised and early stopping allowed to decide (final models stopped at 569–1,101 rounds); 10-trial Optuna search improved validation 1.5695 → 1.5544.

TFT (239,688 params) — gated residual networks, variable selection, LSTM encoder over 96 intervals, interpretable attention. ST-GNN (35,432 params) — 2 graph-attention layers over first-ring cell adjacency + GRU over 24 intervals. Both hand-written, trained on a free Kaggle T4 in ~23 GPU-minutes. Scaling statistics fitted on TRAIN only and baked into the exported bundle, so leaking through normalisation is structurally impossible.

Answering RQ3 carefully

At H3-8, TFT won WAPE (0.3523 vs 0.3573) and ST-GNN won Hotspot F1 (0.7260 vs 0.7248) — both landing exactly where their architectures predict. Both reversed at S2-13, where LightGBM took MAE, WAPE and Hotspot F1 outright.

Why that matters

Two sub-1% margins that flip under a change of tiling scheme are noise, not evidence. Stopping at H3-8 would have produced a more interesting story that happens to be wrong. Both are still reported — suppressing them would be selective.

The honest caveat

The deep models were stopped at 8 epochs and all four were still improving on their final epoch. LightGBM ran to convergence. So the claim is "a tuned LightGBM beats an 8-epoch TFT and ST-GNN", not "gradient boosting beats deep learning". LightGBM is clearly the better value — 48 minutes of CPU and it won — but the deep models weren't given their best shot.

8. Operations — and a negative result

No dock-occupancy data exists for 2023–24, so capacity is estimated from the 95th percentile of daily cumulative net-flow range: median 15 docks across 1,496,558 station-days. 1.73% of station-days are infeasible without assuming staff intervened, and are flagged rather than forced to fit.

Forecast driving the rebalancerService levelUnservedMoves
No rebalancing0.99588,5400
Perfect foresight0.994012,2942,615
LightGBM0.994211,9042,107
Seasonal Naive0.993912,3912,699

(a) Among forecasts, LightGBM beat even perfect foresight — 11,904 unserved vs 12,294. Not a paradox: LightGBM under-forecasts (73% of its worst errors), so it triggers 2,107 moves instead of 2,615. Where moving is harmful, restraint wins.

(b) Rebalancing itself doesn't pay, and the cause is granularity. 321 cells aggregate 2,459 stations — ~115 docks per cell against ~3 trips per interval. A cell that large cannot run dry, so doing nothing already serves 99.58% and every move strips bikes from cells that need them later. Proving rebalancing value needs station-level inventory data that doesn't exist. Reporting a positive result here would have required tuning thresholds until the sign flipped.

Because the API endpoints and the assistant call the same tool functions, the map and the chat can never show different numbers.

All five models serve from one engine — LightGBM 0.3 s warm, ST-GNN 0.17 s, TFT 0.40 s. The deep models need a separate serving path because they consume a tensor window of history (24 intervals for the graph model, 96 for the transformer), not a single feature row.

Three approximations, each labelled in the UI

  • Cell → station. Models forecast ~0.74 km² cells holding ~8 stations. Station numbers are the cell forecast × that station's historical share of its cell's trips. Shares sum to exactly 1.000 across all 321 cells. Flagged approximate: true everywhere.
  • Demand, not availability. We forecast trips, not dock occupancy, so the app reports flow pressure ("bikes leaving fast" / "balanced" / "docks filling up") rather than inventing a bike count.
  • Nothing is live. Models cover 2023–24, so "now" maps to the equivalent 2024 weekday and time, labelled typical conditions.

Places without a maps API

Geocoding uses our own data: 2,459 station names (mostly NYC intersections) plus 19,011 landmarks already geocoded by the events pipeline. Index builds in 0.19 s. Matches below a confidence floor are flagged — "Wall Street" genuinely fails, because Citi Bike names that area differently, and admitting that beats teleporting the user to Brooklyn.

The honesty rule in the assistant

Why the chatbot won't blame a street fair

The natural thing for a chatbot to say is "demand is high because there's a festival nearby". That would be a fabrication — the ablation tested events twice, the second time with 4× the coverage, and measured −0.01%. The deployed model doesn't use events at all.

So tools return drivers (features the model genuinely uses) separately from context (events, weather — each carrying influences_forecast: false). A real explanation reads: "the last hour averaged 91.0 pickups per 15 min, 27% above this cell's usual Wednesday 17:00 level; the same slot last week saw 151."

Three interchangeable brains — Mistral, Claude, or a deterministic router that needs no key so a fresh clone works with zero setup. All return the same payload shape; the LLM paths degrade to the router on any failure.

Walking directions — two graphs, two jobs

Which dock? A station graph where candidates are scored on walking_metres + availability_penalty — a draining dock costs up to 550 virtual metres, so a dock 200 m further with bikes arriving can win. That is the point of putting a forecast behind a router.

How do you walk there? The walkable street network pulled from OpenStreetMap via Overpass, fed to the same A*. Identical algorithm, real edges. The heuristic is great-circle distance — admissible, so A* still finds the optimal path.

The old estimate was also wrong — straight-line × 1.3 overstated by 28%. If Overpass is unreachable it falls back with follows_streets: false, and that flag reaches the UI.

Interface

Map-first with a sliding bottom sheet. Four keyless vector basemaps (OpenFreeMap Liberty by default — full buildings and POIs); MAPTILER_KEY unlocks more. Vector rather than raster specifically so the demand overlay sits beneath the label layers and street names stay readable. The heatmap is off by default — searching pulses just the one cell — and 2,391 real Citi Bike docks are drawn with their names.

BugWhat happened and how it was caught
Silent-drop in de-duplication WHERE key NOT IN (…) evaluates to NULL — not TRUE — for a NULL key, so those rows were dropped with no rule attributed. Caught by the waterfall failing to reconcile: 7 + 3 ≠ 12.
Partitioned write discarded 97% Polars names every partition file 00000000.parquet and rewrites the directory, so each batch replaced the last — only 35 of 1,483 cells survived. Now writes via DuckDB and asserts on-disk counts match.

11. Limitations

Data

  • No dock occupancy exists — capacity and inventory are estimates, flagged everywhere.
  • Traffic covers arterials only; 46 of 128 links within 500 m of a station. 45 days of outages.
  • Events are permits only — no MSG or Barclays; 25% of locations couldn't be geocoded.
  • 255 stations that really operated are missing from the official roster.

Models & app

  • Deep models undertrained (8 epochs, still improving).
  • Training subsamples rows; validation and test never do.
  • No per-station model — station answers are disaggregated.
  • MAPE deliberately absent: most cells are zero.
  • Nothing live; runs locally, not deployed.

Highest-value next step: wire in Citi Bike's live GBFS feed — free, no key, gives real bikes-available per station. That converts availability from an inference into a measurement. Then train the deep models to convergence to settle RQ3 properly.

In closing

The most valuable output isn't the 1.14 MAE. It's the decisions where the honest answer was less impressive than the available one: that rebalancing didn't help, that two apparent deep-learning wins were noise, that traffic and weather and events earned nothing across two separate tests, and that we can't tell you how many bikes are at a dock because nobody published that data.

Every caveat here exists so the numbers that are claimed can be relied on.

13. Summary for a CV

One-line version

Built an end-to-end spatiotemporal ML system forecasting NYC bike-share demand from 79M trips, benchmarking gradient boosting against a Transformer and a Graph Neural Network across two spatial indexing schemes, and deployed it as an agentic map application with A* routing.

Bullet version

  • Built a 79M-row spatiotemporal forecasting pipeline (Polars + DuckDB + Parquet) processing 15 GB of raw trip data into a dense 104M-row panel; achieved 1.14 MAE on a held-out test set, 38% better than the seasonal baseline.
  • Trained and benchmarked four model families across two spatial systems — LightGBM (Optuna-tuned, Poisson objective), a hand-written Temporal Fusion Transformer, a Spatio-Temporal Graph Neural Network with graph attention, and Seasonal Naive — on a six-config matrix over Uber H3 and Google S2 grids.
  • Identified that standard accuracy metrics are invalid for comparing spatial resolutions (MAE, WAPE and Hotspot-F1 gave three different winners) and introduced a baseline-relative skill score that removes the scale effect.
  • Designed a feature ablation over 168 features in 8 families, proving that weather, events and traffic contribute ~0% — re-running the study at 4× traffic coverage to confirm the negative result rather than accept it at face value.
  • Prevented data leakage with 35 automated tests that re-derive every lag feature by an independent join; 166 tests total, with phase gates verified by scripts reading the produced artifacts.
  • Deployed a FastAPI + MapLibre application with an LLM tool-calling agent (Mistral / Claude, plus a dependency-free deterministic fallback), including A* pathfinding with an admissible heuristic over an OpenStreetMap walking graph.
  • Trained deep models on a free Kaggle T4 GPU by exporting a 557 MB tensor bundle, shipping the model definitions alongside the data so the remote run could not diverge from the repository.

Talking points for an interview

  • "Why is MAE the wrong metric here?" — the cross-resolution analysis in §6 is the strongest single result and shows metric literacy beyond running sklearn.metrics.
  • "Tell me about a bug you found." — the NULL-key silent drop (§10) was caught by an arithmetic identity deliberately built into the cleaning step, not by luck.
  • "When did the data surprise you?" — LightGBM out-performing a perfect forecast at rebalancing (§8), because under-forecasting made it act less often.
  • "How do you keep an LLM honest?" — tools return caveats attached to the data, so the model cannot describe events as a cause when the ablation measured them at −0.01%.
